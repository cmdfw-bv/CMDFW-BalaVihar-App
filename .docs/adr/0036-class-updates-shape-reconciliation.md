# ADR-0036: `class_updates` canonical shape reconciliation, explicit `meeting_date`, and a single session-weekday column — integration of issue #21 and issue #23

**Status:** Closed · **Date:** 2026-07-28 · **Deciders:** Project owner + architect
**Governs:** System → `core-schema-and-rls` (`.docs/specs/system/core-schema-and-rls.md`, schema addendum) · consumed by Teacher → `class-update-and-home-feed` (`.docs/specs/teacher/class-update-and-home-feed.md`, PR #48) and Coordinator → `compliance-dashboard` (`.docs/specs/coordinator/compliance-dashboard.md`, PR #50). **Supersedes the "minimum shape" paragraph of ADR-0034** (`class_updates` is System-owned) under that ADR's own escape clause; ADR-0034's *ownership* decision stands unchanged. **Amends ADR-0035** (`class_meetings` calendar) to read `sessions.day_of_week` instead of introducing `sessions.meeting_weekday`. Does not modify ADR-0031 or ADR-0032, both of which stand as written.

### Context

Issue #21 (Teacher class update & home feed, PR #48) and issue #23 (Coordinator compliance dashboard, PR #50) were refined, designed, and built in parallel from divergent bases — §12.6 parallel Units of Work working as intended. Both independently created a table named `class_updates`, and PR #50 additionally branched from `2b4524c`, **before** ADR-0031's `sessions.day_of_week` landed in `main` via #49. Neither divergence is visible as a git conflict, and neither is caught by CI.

**1 — Two incompatible `class_updates` tables.**

| | PR #48 `20260724120400` | PR #50 `20260724201631` |
|---|---|---|
| columns | `class_id, posted_by, body, homework, created_at` | `class_id, meeting_date, posted_by, posted_at` |
| `class_id` FK | `on delete restrict` | `on delete cascade` |
| unique | none (many updates per class) | `(class_id, meeting_date)` |
| RLS policies | **7** (teacher/student/parent/coordinator/org select + inserts) | **0** — deliberate lockdown per ADR-0034 |
| child tables | `comments` + retention fields + length caps | none |

Both use `create table if not exists`, so the collision **fails silently rather than loudly**. PR #48's timestamp sorts first, so on a fresh `supabase db reset` PR #50's `create table` becomes a no-op. `get_session_compliance_for_staff` is `plpgsql`, whose body is not validated against the catalog at creation time — it creates cleanly, `db-and-rls` passes, and it then raises `column cu.meeting_date does not exist` **at runtime**, the first time a Coordinator opens the dashboard. In the reverse merge order the failure is equally silent in the other direction: PR #48's older timestamp becomes an out-of-order migration and `if not exists` means `body`/`homework` are never created, breaking the Teacher feature instead.

ADR-0034 explicitly anticipated this: *"that item's governing ADR for the table itself is this one … **unless its write requirements turn out to need a schema shape this ADR didn't anticipate**."* PR #48's requirements — a post body, an optional homework field, threaded public/private comments (ADR-0032), retention fields, length caps — are exactly that shape. This ADR is that clause firing, not a re-litigation of ownership.

**2 — Two columns for the session weekday.** PR #50 adds `sessions.meeting_weekday smallint not null check (between 0 and 6)`. `main` already carries `sessions.day_of_week smallint not null check (between 0 and 6)` — identical type, identical `0=Sunday` convention matching `extract(dow from …)`, identical meaning — migrated, seeded for all 8 sessions, pgTAP-covered (`160_session_weekly_schedule.sql`), read by the shipped attendance UI, and signed off twice on 2026-07-24 (ADR-0031).

The divergence is not hypothetical and does not require a schedule change. The confirmed catalog of record (doc 1 §9a) puts the pilot session **Frisco F3 on Sunday, 2:00–3:30 PM** (`day_of_week = 0`). PR #50's seed sets the same session's `meeting_weekday = 2` (**Tuesday**). On merge, one row carries both values simultaneously: the attendance UI reads `day_of_week` and offers Sundays where teachers mark; `generate_class_meetings_for_session` reads `meeting_weekday` and generates Tuesday meetings; the dashboard scores those Tuesdays, finds nothing, and reports every F3 class **0% / 0% non-compliant** — with the schedule never having changed. Separately, `main`'s second `insert into sessions` (seven sessions, `seed.sql:130`) supplies only `day_of_week`, so PR #50's `not null`-with-dropped-default column makes `supabase db reset` **fail outright** unless all 7 seed inserts and 6 pgTAP fixtures are hand-edited to carry both columns in permanent lockstep.

### Options Considered

**Which `class_updates` shape is canonical**

- **PR #48's shape canonical; PR #50 adapts** (chosen) — Pros: PR #48's shape is a strict superset driven by real product requirements (body, homework, `comments` with ADR-0032's privacy flag, retention, length caps), all of it built, reviewed, and CI-green; PR #50 only ever *reads an aggregate* off this table (AC6: read-only) and needs one column from it. The consumer adapts to the producer's shape, which is the direction ADR-0034's own ownership reasoning already points. Cons: PR #50 must re-stamp migrations and rework its schema migration and one pgTAP file.
- **PR #50's shape canonical; PR #48 adapts** — Pros: none identified beyond PR #50 needing no rework. Cons: would delete `body`, `homework`, `comments`, retention fields, and 7 RLS policies from the larger, green, fully-reviewed PR, and leave the Teacher feature with no way to store the post it exists to store. Rejected outright.
- **Two tables** (e.g. `class_updates` for Teacher content + `class_update_meetings` for the compliance signal) — Pros: neither branch changes. Cons: two tables modelling one concept, joined on every read, with no consumer wanting them apart; guarantees drift and doubles the RLS surface on a minors'-adjacent table. Rejected.

**How the compliance metric resolves a meeting date**

- **Explicit `meeting_date`, `not null`, with a composer meeting-date picker** (chosen — **business requirement**, project owner 2026-07-28) — Pros: a teacher who misses a week can post for the meeting it actually belongs to, and a coordinator's dashboard reflects what happened rather than when it was typed; the metric becomes exactly true instead of approximately true. Cons: adds a picker to the compose screen and one column to the table; the picker needs `class_meetings`, so it must be built after that table exists.
- **Derive from `created_at::date`** — Pros: zero schema and zero UI change. Cons: `created_at` is `timestamptz`; a teacher posting 9:30 PM Central on the meeting Sunday stores `02:30Z` the next day, so `created_at::date` reads as **Monday** under a UTC server `TimeZone` and the class is marked non-compliant despite the teacher having posted on time — the same UTC-vs-Central boundary defect the PR #50 review already caught twice (`enrolled_at <= meeting_date`, `meeting_date <= current_date`). A teacher who posts the morning after has no way to make the meeting show as covered. Rejected.
- **Nullable `meeting_date` auto-stamped to the most recent past meeting, no picker** — Pros: correct for the common case with a ~1-line composer change and no new UI. Cons: silently mis-attributes any deliberately backdated post and offers no way to correct it; does not satisfy the stated business requirement that a teacher can post *for a specific past meeting*. Rejected in favour of the explicit option.

**Session weekday column**

- **Drop `meeting_weekday`; read `sessions.day_of_week`** (chosen) — Pros: one column for one fact, already holding the correct §9a catalog values for all 8 sessions and already tested; keeps `supabase db reset` working; removes the only reason PR #50 edits `supabase/tests/010, 040, 060, 100, 150, 999`, cutting its conflict surface from 11 files to 5. Cons: requires amending ADR-0035's text (which is being renumbered before it enters the record anyway).
- **Keep both, synchronized** — Pros: no rework on PR #50. Cons: 13 insert sites (7 seed rows + 6 pgTAP fixtures) must set both columns identically forever, and the very first attempt already got it wrong (F3 as Tuesday against a Sunday catalog); a mismatch produces a silently wrong dashboard with no error. Would at minimum require a `check (meeting_weekday = day_of_week)` to fail loudly — which is an argument for there being one column. Rejected.

### Decision

1. **PR #48's `class_updates` is canonical.** `id, class_id → classes on delete restrict, posted_by → auth.users on delete set null, body not null, homework, created_at`, plus the `comments` child table, ADR-0032's privacy model, retention fields, and length caps. PR #50 **removes its own `class_updates` definition entirely** (table, `enable row level security`, grants, revokes) from its schema migration.
2. **`class_updates` gains `meeting_date date not null`**, added by PR #50 in its own migration using ADR-0031's established add → backfill → not-null shape. **No unique constraint** on `(class_id, meeting_date)` — PR #48's model permits several updates per class, and the compliance metric only asks `exists`, so uniqueness would constrain the product for no metric benefit.
3. **The Teacher compose screen gains a meeting-date picker**, sourced from `class_meetings` via the existing `class_meetings_teacher_select` policy, defaulting to the most recent scheduled meeting on or before today. Because PR #50 merges last, this change is made by PR #50 against PR #48's by-then-merged `ComposeClassUpdateScreen.tsx` — **PR #48 itself requires no changes.**
4. **PR #48's RLS posture governs `class_updates`**, superseding ADR-0034's zero-policy stance for this table. Parent and Student read access is a product requirement of the home feed and is governed by ADR-0032. The Coordinator's compliance read continues to go through `get_session_compliance_for_staff` (SECURITY DEFINER, scope-checked, audited per ADR-0019) rather than a direct grant — unchanged by this ADR, and unaffected by the presence of policies since SECURITY DEFINER bypasses RLS by design.
5. **`sessions.meeting_weekday` is not created.** PR #50 drops the three `alter table sessions` statements, and `generate_class_meetings_for_session` reads `v_session.day_of_week`. `sessions.day_of_week` (ADR-0031) is the single source of truth for session weekday, holding the doc 1 §9a catalog.
6. **PR #50's ADRs are renumbered before entering the record** — `0030-class-updates-system-owned` → **ADR-0034**, `0031-class-meeting-calendar` → **ADR-0035** — since `main` already owns 0030/0031 and PR #48 owns 0032/0033. Both are unmerged drafts that have never been part of the record, so correcting their text in place is not an edit to a Closed ADR.

### Consequences

- **PR #50 carries all of the reconciliation work.** PR #48, #54, and #51 are unaffected by this ADR. The merge order is **#48 → #54 → #51 → #50**; PR #50's migrations must be re-stamped to `20260729*` so they sort after PR #48's `20260728150000`, or they become out-of-order migrations against any already-migrated environment.
- **`supabase/tests/160_class_meetings_schema.sql` (renumbering to `180_`) must be reworked, not just renamed.** Its line 86 insert omits `body`, which is `not null` in the canonical table, and its line 88 assertion — `class_updates has zero read policies` — becomes false once `class_updates_org_select` exists. Both fail after PR #48 merges; the `plan(12)` count changes accordingly. This is the one place the silent schema collision becomes a loud CI failure, and it should stay loud.
- **`core-schema-and-rls.md`'s canonical schema table gains `class_updates` and `class_meetings`** as an ADR-0034/0035/0036 addendum, in the same shape ADR-0021 and ADR-0031 used to amend that already-Built spec.
- **Hardening item for `/build`, not decided here:** with `meeting_date` client-supplied on insert, `class_updates_teacher_insert`'s `with check` should additionally confirm the date corresponds to a real `class_meetings` row for the teacher's own class, so a teacher cannot post against an arbitrary date. Scope is already bounded by the policy's existing `class_id = scope_id` clause, so this is defence-in-depth rather than a leak.
- **Residual scope:** ADR-0031's deferral of holiday/skip-week exceptions still stands. `class_meetings.status = 'cancelled'` now provides a natural place to model those when a real pilot need surfaces — a follow-up ADR, not assumed here.
- **Process note.** Two parallel Units of Work each created the same table and each added a column for the same fact, and nothing — not git, not `db-and-rls`, not either code review — surfaced it; both defects were found only by a cross-PR integration read. Worth a `/architect` pre-merge integration check whenever two or more open PRs carry migrations, rather than relying on per-PR review.
