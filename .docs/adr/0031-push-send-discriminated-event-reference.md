# ADR-0031: `push-send` contract extended to a discriminated event reference (ADR-0028 addendum)

**Status:** Closed · **Date:** 2026-07-24 · **Deciders:** Project owner + architect
**Governs:** System → `notifications-infra` (`.docs/specs/system/notifications-infra.md`), consumed by Teacher → `class-update-and-home-feed` (issue #21).
**Extends:** ADR-0028 (push dispatch is client-invoked). Does not reopen ADR-0028's core decision (client-invoked, service-role, re-derive-server-side) — fixes the one thing it left open: the exact shape of a second trigger source's request.

### Context

ADR-0028 fixed the invocation *pattern* — the client writes its row under RLS, then calls `push-send` with a reference to it, and the function re-derives recipients server-side rather than trusting the caller — and explicitly anticipated `#21 class-update-and-home-feed` as a second caller, "without rework." But `notifications-infra`'s already-signed-off `/design` (still pre-`/build`) fixed a *concrete* contract narrower than that: `POST /push-send` body is `{ message_id }` only, and phases 3–5 hardcode a `messages` lookup, a `conversation_participants` recipient-derivation, and a `conversations.kind`-keyed payload string. That's narrower than the same spec's own AC#3, which promises a generic function ("given target `user_id`s plus a PII-free payload"). Since `notifications-infra` hasn't been built yet, the contract is still correctable — but `class-update-and-home-feed`'s `/design` needs a fixed shape to build against now, and the mismatch between AC#3 and the actual Design section is worth closing explicitly rather than letting `/build` discover it.

### Options Considered

- **Discriminated request body (chosen)** — one function, body is `{ message_id }` **or** `{ class_update_id }` (validation rejects both-present or neither-present). Shared phases: 1 (auth via `getUser`), 2 (validate), 6 (fan-out/dispatch via `web-push`), 7 (response shape). Branch-specific phases 3–5 (load + authorize + derive recipients + payload copy) differ per event type but follow the identical shape: load the referenced row, reject if `caller_user_id` isn't the row's own author (`sender_user_id` for a message, `posted_by` for a class update — closes the same notification-spam vector phase 3 already closes for chat), derive recipients from the DB, dispatch a PII-free payload. Pros: one function, one secret surface (VAPID private key stays in exactly one place) — matches ADR-0028's single-trusted-computation-point rationale; each event type still fully re-derives its own recipients server-side, so ADR-0028's "never trust the caller for who gets notified" holds for both callers, not just the first. Cons: the function's internal branching grows with each new trigger source — acceptable; it's the same shape ADR-0028's own consequences already predicted ("every future trigger source... follows the same shape... no DB-side wiring needed per new event type"), just naming the concrete mechanism that sentence left implicit.
- **Generic passthrough (`user_ids` + `payload`, caller-supplied)** — matches AC#3's literal wording most directly. Rejected: this is exactly what ADR-0028 was written to prevent — a service-role function that trusts the caller for *who* gets notified is a spoofable notification path (an authenticated-but-unrelated caller could target arbitrary `user_id`s), the same class of gap phase 3's caller-must-be-sender check already exists to close for the `messages` case.
- **Separate function** (e.g. `push-send-class-update`) — rejected: duplicates the VAPID-secret wiring and the `web-push`/cleanup/response logic for a 3-non-technical-volunteer-maintainer team to keep in sync across two functions; contradicts ADR-0028's stated preference for minimal new operational surface.

### Decision

Extend `push-send`'s request contract to a discriminated union: `{ message_id: uuid }` XOR `{ class_update_id: uuid }`. For the `class_update_id` branch: load `class_updates` (id, class_id, posted_by) by id — not found → `200 {status:'noop'}`; `caller_user_id !== posted_by` → `403`. Derive recipients as all Students + Parents currently enrolled in `class_id` (via `enrollments`) — the poster is not their own recipient (mirrors the existing self-notification exclusion). Payload copy stays PII-free and generic (no student name, no class-specific identifiers beyond what the `messages` branch already allows via `conversations.kind`-only wording) — the exact string is `class-update-and-home-feed`'s `/design` decision, following this shape, not a new one.

### Consequences

- `notifications-infra.md`'s Design section (push-send contract, phase 3, request body) is amended now — by this `/architect` pass — to describe the discriminated body instead of the `{ message_id }`-only shape, so `/build` doesn't ship a narrower contract than AC#3 promises and #21 needs.
- `class-update-and-home-feed`'s `/design` owns the `class_update_id` branch's exact recipient query and payload copy string as an extension of this ADR's shape — not a fresh invocation-mechanism decision.
- `push-send` remains the single trusted computation point and the only place the VAPID private key lives — every future trigger source (a third caller, if one ever arrives) adds a branch to this same discriminated body, not a new function.
- pgTAP/adversarial coverage (constitution rule #4, §11.3) for the `class_update_id` branch's caller≠poster check and recipient-derivation is a `/test`-stage obligation for `class-update-and-home-feed`, mirroring the existing obligation already recorded for the `message_id` branch in `notifications-infra`.
