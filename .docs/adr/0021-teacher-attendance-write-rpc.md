# ADR-0021: Teacher attendance-write via SECURITY DEFINER RPC (supersedes ADR-0020)

**Status:** Closed · **Date:** 2026-07-09 · **Deciders:** Project owner + architect
**Governs:** System → `core-schema-and-rls` (`.docs/specs/System/core-schema-and-rls.md`). **Supersedes ADR-0020** in full — ADR-0020's premise (audit a client-side Teacher `UPDATE` via a trigger) does not apply once the client-side write path it was auditing is retired. Does not touch ADR-0019's core decision (hybrid RPC for cross-scope **reads** of `students`/`attendance`/`consents`), which stands unchanged.

### Context
While implementing ADR-0020's trigger (Task 11), the TDD RED step stayed red after the trigger was correctly installed (verified via `pg_trigger`). Root-cause investigation (reproduced directly against the database, four independent fixture runs) found the trigger was never the problem: **`attendance_teacher_update` and `attendance_teacher_insert` (shipped in Task 2, commit `033ca8a`, previously "tested green") have never actually been usable by a real client:**
- A Teacher `UPDATE attendance SET status = ... WHERE id = <in-class row>` matches **zero rows**, silently, every time — confirmed reproducible and confirmed fixed by adding a (throwaway, rolled back) Teacher SELECT policy on `attendance`.
- A Teacher `INSERT ... RETURNING *` — what `supabase-js`'s standard `.insert().select()` pattern sends — fails outright with `ERROR: new row violates row-level security policy for table "attendance"`.

Root cause: PostgreSQL RLS requires an applicable SELECT-policy-equivalent visibility check to locate/return rows for `UPDATE` and for any `RETURNING` clause, in addition to the command-specific policy's own `USING`/`WITH CHECK`. Teacher was deliberately given **zero** SELECT policy on `attendance` (ADR-0019: staff reads of minors'-record tables are RPC-only, even for one's own class). No prior test asserted a row-count on a Teacher write (only that it didn't throw), so this defect shipped silently. Checked for the same pattern elsewhere: `consents`' only writer (Parent) already has a matching SELECT policy, so this is isolated to Teacher/`attendance`, not systemic.

### Options Considered
- **Add a Teacher SELECT policy on `attendance` (own class), keep the client-side UPDATE + ADR-0020's trigger** — Pros: smallest diff, makes the existing policy actually work. Cons: directly contradicts ADR-0019's decision that Teacher reads of `attendance` — even for their own class — are not self/parent-scope and must be audited via RPC; a plain SELECT policy reopens that exact surface at a **larger** scale than the `RETURNING`-trick ADR-0020 closed (every ordinary roster/attendance view would use it, unaudited). Rejected.
- **Patch ADR-0020's trigger further** — not viable: the trigger only fires on rows an `UPDATE` actually touches, and the `UPDATE` touches zero rows or errors outright; there's nothing for the trigger to observe. Not a real option, just a restatement of the bug.
- **`SECURITY DEFINER` RPC for the write** (chosen) — mirrors the ADR-0019 read-RPC pattern exactly: `mark_attendance_for_staff(p_enrollment_id, p_class_meeting_date, p_status)` runs as the table owner (bypassing RLS), does its own scope check (Teacher must own the enrollment's class), and performs `insert ... on conflict (enrollment_id, class_meeting_date) do update` (the existing unique constraint from Task 2). Pros: fixes both failure modes (0-row `UPDATE`, erroring `INSERT ... RETURNING`) in one consistent path; since no client SQL can reach `attendance` for Teacher at all afterward, there is no bypassable read surface left — ADR-0020's whole premise stops applying, cleanly. Cons: one more RPC to maintain; Teacher's attendance-marking screen must call the RPC instead of `supabase-js`'s generic `.from('attendance').upsert()`.

### Decision
1. Add `mark_attendance_for_staff(p_enrollment_id uuid, p_class_meeting_date date, p_status text) returns attendance` — `SECURITY DEFINER`, scope-checks the calling Teacher owns the enrollment's class (same check shape as `get_class_attendance_for_staff`), then `insert into attendance (...) values (...) on conflict (enrollment_id, class_meeting_date) do update set status = excluded.status, marked_by = excluded.marked_by, submitted_at = now()`. Out-of-scope calls insert one `audit_log` row (`action='denied'`, `target_table='attendance'`) and return nothing — consistent with the existing ADR-0019 RPCs' denied-logging precedent (doc 3 §11.1 defense-in-depth), even though successful writes are not separately audited (see below).
2. **No `audit_log` row on a successful write** — `marked_by`/`submitted_at` on `attendance` itself already attributes every write to its actor, matching the original design rationale (`core-schema-and-rls.md`'s Data & RLS impact section: "writes are already attributed... so they don't need a redundant audit row"). Once the RPC is the only path to `attendance` for Teacher, there is no bypassable disguised-read surface left for that reasoning to be wrong about.
3. **Retire `attendance_teacher_insert` and `attendance_teacher_update`** (Task 2) — drop both policies; revoke `insert`, `update` on `attendance` from `authenticated` (the `select` grant/policies for Parent/Student are untouched). Teacher's only path to writing `attendance` becomes the RPC.
4. **ADR-0020 is superseded, not extended.** Its trigger (`attendance_after_update_teacher_audit` / `audit_teacher_attendance_access()`) is never built — Task 11 of `core-schema-and-rls.plan.md` is rewritten to implement this RPC instead of the trigger.

### Consequences
- `core-schema-and-rls.md`'s Design addendum section is rewritten to reflect the RPC, not the trigger; Task 11 in the plan is rewritten to match (migration creates the RPC + drops the two Task 2 policies + revokes grants, in one migration; pgTAP proves: Teacher direct `insert`/`update` on `attendance` now returns nothing/fails — locked down like the read RPCs — the RPC succeeds for an in-class Teacher on both a new date (insert branch) and an existing date (update/correction branch), and a denied out-of-scope call produces one `audit_log` row and no data change).
- The Task 11 migration and test file already created for the trigger approach are removed before the RPC migration is written (never shipped, no prod exposure).
- Any future staff-facing screen that marks or corrects attendance must call `mark_attendance_for_staff`, not a generic `.from('attendance').insert()/.update()` — this is the same constraint the existing `get_*_for_staff` RPCs already impose on staff-facing reads, now extended to this one write.
- **Residual scope:** this ADR only covers Teacher's own-class attendance write. No other role writes `attendance` today; if a future item needs Coordinator/Admin attendance correction, it extends this RPC's scope check, not a new pattern.
