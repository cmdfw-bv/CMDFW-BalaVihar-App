# ADR-0031: Explicit class-meeting calendar is the source of truth for expected meeting dates (System-owned)

**Status:** Closed · **Date:** 2026-07-24 · **Deciders:** Project owner + architect
**Governs:** System → `core-schema-and-rls` (`.docs/specs/system/core-schema-and-rls.md`, schema addendum, detailed at `/design`) · consumed by Coordinator → `compliance-dashboard` (`.docs/specs/coordinator/compliance-dashboard.md`) and, later, any Teacher/System item computing an "expected meeting dates" denominator.

### Context

Not flagged in `compliance-dashboard.md`'s refine pass, surfaced during `/architect` review: the schema has no independent record of which dates a class was scheduled to meet. `attendance.class_meeting_date` is a plain `date` column populated only when a Teacher actually submits attendance for that date (`mark_attendance_for_staff`, ADR-0021) — there is no calendar, term schedule, or day-of-week field anywhere upstream of it.

This matters because the compliance dashboard's core purpose is to catch a class with a **zero** submission rate — but a class-meeting-date window with zero `attendance` rows is, under the current schema, indistinguishable between two very different situations: "this class had no scheduled meeting in this window" (AC5's honest `—` placeholder, correctly non-alarming) and "this class had meetings and the teacher submitted nothing for any of them" (full non-compliance — the exact failure mode the dashboard exists to surface as red, not as a quiet dash). Silently defeating AC5's own stated intent ("never a `0%` that would misread... as 'class failed to submit'") in the other direction — a `—` that should have been a `0%` — is just as much a compliance-dashboard failure as the false positive AC5 explicitly guards against. This is a schema-shape gap, squarely the kind of decision §12.10 reserves for `/architect`.

### Options Considered

- **Compute expected dates on the fly from a weekly-cadence field, no stored calendar** — Pros: cheapest, one column, no new table. Cons: cannot represent an individual skip week (e.g. no Balavihar over a holiday weekend) without storing skip dates *somewhere* — so on its own this option doesn't actually resolve the real-world constraint (confirmed with the project owner: some weeks have no Balavihar and a pure weekly-stepping computation would wrongly mark those as expected-but-missed).
- **Explicit calendar table, populated entirely by manual entry** — Pros: most accurate, handles any irregular schedule, no generation logic to get wrong. Cons: asks Coordinator/Admin (non-technical volunteers) to hand-enter every meeting date for an entire session; more upkeep than the weekly-cadence-with-occasional-exceptions reality actually needs.
- **Hybrid — auto-generate the default weekly series into an explicit, editable table; skip weeks applied via the existing CSV-import seam (chosen)** — Pros: keeps the low admin burden of auto-generation for the common case (a session that meets every week on the same day) while still solving the actual constraint raised (occasional skip weeks) through infrastructure that already exists (ADR-0022's CSV import), rather than building a new manual-entry screen. The table itself remains the authoritative, editable record — auto-generation is just how it gets seeded, not a permanent constraint on its contents. Cons: two-step data flow (generate, then apply skips) instead of one; a genuine schema-shape decision to specify precisely at `/design`.

### Decision

1. **`meeting_weekday` is added to `sessions`**, not `classes`. Sessions are already day/time-scoped cohorts in this system (ADR-0014's own context-chip example names a session "Sunday AM"), and every class within a session shares that session's meeting day — so generation runs once per session, not once per class, with no risk of a Friday session's classes generating Sunday dates or vice versa.
2. **A new System-owned `class_meetings` table** (exact column set finalized at `/design`): one row per class × expected date, with a `status` (`scheduled` / `cancelled`) rather than deletion, generated from `sessions.start_date`..`sessions.end_date` stepped by `meeting_weekday`. One generation pass per session covers every class in it.
3. **Skip/holiday weeks are applied via the existing CSV-import seam** (extends ADR-0022's already-built mechanism), letting Coordinator/Admin mark known skip dates for a session once, ahead of time — those rows are set `cancelled`, not deleted, so the record distinguishes "scheduled, then cancelled" from "never scheduled." No new manual single-date-edit UI is built for this.
4. **`class_meetings` becomes the sole source of truth for "expected" dates** for both compliance-dashboard metrics (attendance-submission rate and, once it exists, class-update-posting rate) — replacing any implicit derivation from whether `attendance` rows happen to exist.
5. **Out of scope for this ADR:** retrofitting `mark_attendance_for_staff` to validate the submitted date against `class_meetings` — the existing, already-built RPC (ADR-0021) is left untouched; this is additive schema, not a rewrite (constitution #3). A manual per-date edit screen is also out of scope — cancellations only enter via CSV import for now.

### Consequences

- `/design` for `compliance-dashboard.md` (coordinating the same System-side addendum ADR-0030 requires) must specify `class_meetings`' exact columns, the generation mechanism (a callable RPC invoked at session creation, vs. a one-time migration-time function — pick one), its RLS (session-scoped read, matching `classes`/`sessions`' existing posture), and how the new session-scoped aggregate RPC (flagged in the brief's second open item — replacing N per-class `get_class_attendance_for_staff` calls) joins against `class_meetings` to compute both metrics' denominators, honoring the mid-window-roster-change edge case already specified (AC/edge cases in the brief) on a per-date basis.
- The CSV-import skip-dates extension is a small addition to the existing import function/spec (ADR-0022), not a new external processor or new residency/PII surface.
- **Residual risk:** a session's meeting weekday changing mid-session (a one-off day-of-week move) is not modeled — flagged as a future edge case if it surfaces at pilot, not solved speculatively here (mirrors ADR-0018's own precedent for deferring unmodeled real-world complexity rather than over-building for it).
