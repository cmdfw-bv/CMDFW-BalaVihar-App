# ADR-0030: Teacher attendance roster resolves `enrollment_id` via direct `enrollments` read (ADR-0019/ADR-0021 addendum)

**Status:** Closed · **Date:** 2026-07-23 · **Deciders:** Project owner + architect
**Governs:** Teacher → `attendance-ui` (`.docs/specs/teacher/attendance-ui.md`). Resolves the brief's flagged hard dependency: `get_class_roster_for_staff` (ADR-0019) returns `setof students` with no `enrollment_id`, but `mark_attendance_for_staff` (ADR-0021) requires `p_enrollment_id` — and for a date with no existing `attendance` row, there is no `attendance` row to join through either. Does not modify ADR-0019 or ADR-0021's decisions; both stand unchanged.

### Context
The attendance-marking screen needs, per visible roster row, the `enrollment_id` to pass to `mark_attendance_for_staff`. The only existing roster RPC (`get_class_roster_for_staff`) returns student rows, not enrollment rows, and was designed that way deliberately — ADR-0019 scoped its hybrid RPC-audit pattern to the minors'-data tables (`students`, `attendance`, `consents`) only. `enrollments` was never included in that set: it is a linkage table (student_id, class_id, session_id, status) with no student-identifying columns of its own, and it already carries a plain RLS policy for Teacher (`enrollments_teacher_select`, `supabase/migrations/20260709032818_core_operational_rls_policies.sql:188`) scoped identically to the RPCs (`enrollments.class_id = scope_id`), plus an existing `grant select on enrollments to authenticated`. This was not exercised by any UI yet, so the brief's authors didn't have it in view when flagging the gap.

### Options Considered
- **Direct client read of `enrollments`** (chosen) — Pros: zero migration; uses grants and an RLS policy that already exist and already carry the exact same scope check as the RPCs it would otherwise duplicate; `enrollments` is explicitly outside ADR-0019's minors'-data table set, so this isn't a new exception carved out of that model, it's the model already excluding this table. Cons: the roster screen now does two reads (RPC for student names/details + direct table read for enrollment linkage) that the client must correlate by `student_id`; if `enrollments` is ever reclassified as minors'-data (e.g. it grows PII columns), this read moves under the RPC pattern too — a follow-up ADR at that time, not assumed here.
- **Extend `get_class_roster_for_staff`'s return shape** to include `enrollment_id` — Pros: single audited call, roster payload already carries everything needed. Cons: changes a Closed ADR-0019 RPC's return contract; every existing/future caller of that RPC must be re-verified against the new shape; a migration is needed for a fix that has a zero-migration alternative. Rejected as unnecessary churn on a shipped, audited function.
- **New additive RPC** (e.g. `get_class_roster_with_enrollment_for_staff`) returning roster+enrollment_id together — Pros: doesn't touch the existing RPC's contract. Cons: near-duplicate roster-fetch logic to maintain against `get_class_roster_for_staff` long-term, plus new ambiguity over whether/how audit-log rows deduplicate if a screen ever needs both. Rejected — no material benefit over the direct-read option here since `enrollments` isn't an audited table in the first place.

### Decision
The Teacher attendance-marking screen resolves `enrollment_id` by reading `enrollments` directly (`select id, student_id from enrollments where class_id = <teacher's scope_id> and status = 'active'`), relying on the existing `enrollments_teacher_select` RLS policy and existing `select` grant — no migration required. The client joins this by `student_id` against `get_class_roster_for_staff`'s output to build the roster-row → `enrollment_id` map needed for `mark_attendance_for_staff`. `get_class_roster_for_staff` and `mark_attendance_for_staff` are unchanged; ADR-0019 and ADR-0021 stand as written.

### Consequences
- `/design` for `attendance-ui` specifies this as two reads (RPC + direct `enrollments` select) correlated client-side by `student_id`, not a single combined call.
- No new migration, RLS policy, or grant is needed for this item; `/build`'s adversarial RLS coverage should still confirm (likely already covered by `core-schema-and-rls`'s existing suite) that a Teacher's `enrollments` read stays scoped to their own `class_id` and that out-of-scope classes return zero rows.
- **Residual risk:** if `enrollments` later gains student-identifying or otherwise sensitive columns, its Teacher-visible read path should be revisited against ADR-0019's minors'-data criteria — a follow-up ADR at that time, not assumed here.
