# ADR-0020: Teacher attendance-write audit trigger (ADR-0019 addendum)

**Status:** Superseded by [ADR-0021](0021-teacher-attendance-write-rpc.md) · **Date:** 2026-07-09 · **Deciders:** Project owner + architect

> **Superseded 2026-07-09, same day:** implementing this ADR's trigger (Task 11) revealed during TDD that its premise doesn't hold — the client-side `attendance_teacher_update` it audits never actually executes for a real client (Postgres RLS blocks the row lookup; see ADR-0021). The trigger was never built. Body below is kept for the record, unedited.
**Governs:** System → `core-schema-and-rls` (`.docs/specs/System/core-schema-and-rls.md`). Extends ADR-0019; does not supersede it — the hybrid RPC model for cross-scope staff reads of `students`/`attendance`/`consents` stands unchanged. This addendum closes a bypass of that model discovered during final review (deferred from the item's build, tracked in project memory).

### Context
`attendance_teacher_update` (`supabase/migrations/20260709032818_core_operational_rls_policies.sql`) lets a Teacher `UPDATE ... RETURNING *` any attendance row in their own class, with a `USING`/`WITH CHECK` clause scoped correctly to their class. Under ADR-0019, Teacher reads of `attendance` are not self/parent-owned data — they're meant to go exclusively through the audited `get_class_attendance_for_staff` RPC, the same as Coordinator/BV Coordinator/Admin. A no-op `UPDATE ... SET status = status ... RETURNING *` gives a Teacher full row data (any column) with zero `audit_log` entry, bypassing that pattern entirely. It is same-scope (no cross-scope leak — a Teacher still can't reach another class), but it contradicts the decided design, which requires an audit trail for every staff read of a minor's record regardless of scope correctness.

The design section of `core-schema-and-rls.md` rationalized `audit_log` as covering reads only ("writes are already attributed via `marked_by`/`granted_by`, so they don't need a redundant audit row") — correct for genuine writes, but that reasoning doesn't hold once `RETURNING` is used as a disguised read.

### Options Considered
- **Add an `AFTER UPDATE` trigger on `attendance`** (chosen) — Pros: unlike `SELECT`, `UPDATE` triggers fire natively in Postgres, so this closes the gap with a standard trigger, not a new RPC/pattern; writes one `audit_log` row (`action='read'`, `target_table='attendance'`) per teacher-initiated update, capturing the `RETURNING`-as-read case along with genuine writes. Cons: every legitimate attendance-marking update now also produces an audit row, which is redundant with `marked_by` attribution for the write itself — accepted as the simplest correct fix rather than trying to distinguish "real" writes from no-op reads at the trigger level (that distinction isn't reliably detectable in SQL without excess complexity).
- **Accept as intentional carve-out (ADR addendum, no code change)** — Pros: zero migration churn, same-scope-only so no cross-scope leak. Cons: leaves an audit-free bulk-read path open (a Teacher can no-op-update every row in their class to dump full attendance data with no trail) — contradicts ADR-0019's literal "every staff read of a minor's record is audited" decision; rejected as too weak given non-negotiable #6 and ADR-0019's own precedent of erring toward completeness over convenience for staff (non-self-scope) roles.
- **Revoke `RETURNING`/column-level `SELECT` on `attendance` for the teacher role** — Pros: would close the read path without adding audit noise. Cons: Postgres does not gate `RETURNING` behind a separate `SELECT` privilege from `UPDATE` — a role with `UPDATE` privilege can `RETURNING` the columns it updates regardless of `SELECT` grants, so this isn't actually enforceable at the grant level; rejected as not viable.

### Decision
Add an `AFTER UPDATE` trigger on `attendance` that fires whenever `auth.jwt()->>'active_role' = 'teacher'`, inserting one `audit_log` row (`action='read'`, `actor_user_id=auth.uid()`, `actor_role='teacher'`, `target_table='attendance'`, `target_id=NEW.id`, `target_student_id` resolved via `NEW.enrollment_id → enrollments.student_id`). This applies to every Teacher-initiated update to an attendance row, including no-op updates used purely to `RETURNING` data — closing the audit-free read path without changing the RLS scope rules (Teacher still only reaches their own class) or the RPC pattern for Coordinator/BV Coordinator/Admin reads, which is unaffected.

### Consequences
- A new migration adds the trigger + trigger function; the pgTAP adversarial suite gains an assertion: a Teacher `UPDATE`ing (including a no-op update) an in-class attendance row produces exactly one `audit_log` row with `action='read'`.
- Genuine attendance-marking writes (the common case) now also produce an `audit_log` row in addition to the existing `marked_by` attribution — accepted redundancy, not a defect; it's the cost of closing the `RETURNING`-as-read path without a more complex real-write-vs-no-op distinction.
- `attendance_teacher_insert` (plain `INSERT`, no `RETURNING` risk beyond the row just created by the same actor) is unaffected — this addendum only concerns `UPDATE`.
- Owner: **System**, folded into `core-schema-and-rls` as a follow-up migration (not a new item) — routed to `/design`/`/migration` to add the trigger to the existing table.
