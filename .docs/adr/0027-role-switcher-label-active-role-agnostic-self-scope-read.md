# ADR-0027: Role-switcher labels are an active-role-agnostic self-scope read (ADR-0019 addendum)

**Status:** Closed · **Date:** 2026-07-17 · **Deciders:** Project owner + architect
**Governs:** System → `core-schema-and-rls` (`.docs/specs/System/core-schema-and-rls.md`). Extends ADR-0019; does not supersede it — the hybrid model (plain RLS-select for self/parent, audited RPC for staff cross-scope reads) stands unchanged. This addendum covers a third shape neither pathway anticipated, surfaced during code review of `client-auth-session` (issue #17).

### Context
`resolve_my_scope_labels()` (`supabase/migrations/20260714224917_resolve_my_scope_labels_rpc.sql`, extended by `20260715030000_resolve_parent_scope_label.sql`) is a `SECURITY DEFINER` function that resolves a friendly scope label for **every** `user_roles` row the caller owns — not just the currently active one — because the role-switcher UI must display a label for every held role simultaneously (ADR-0014/ADR-0023). It is keyed on `auth.uid()` rather than the JWT's `active_role` claim; test cases 2/8/9 in `supabase/tests/150_scope_label_resolution_rpc.sql` prove this is deliberate (identical result regardless of which held role is active, and forged `active_role`/scope claims have zero effect).

For the `role = 'parent'` branch, this reads children's first names (minors' PII) via `family_members` → `students`. ADR-0019 decided minors'-data reads split into exactly two pathways: **(a)** Parent/Student self-scope reads via plain RLS-scoped `select`, unaudited, gated by `auth.jwt()->>'active_role'`; **(b)** staff cross-scope reads via an audited `SECURITY DEFINER` RPC. `students_parent_select` (`core_operational_rls_policies.sql`) already grants a parent direct, unaudited read of their own children's names — but only while `active_role = 'parent'`.

`resolve_my_scope_labels()`'s parent branch doesn't fit either pathway cleanly: it's a `SECURITY DEFINER` RPC (pathway b's mechanism) returning self/parent-scoped data (pathway a's exemption), and it deliberately ignores the `active_role` gate that pathway (a) relies on — so it can disclose a child's name in a session where `parent` isn't even the active role. No cross-family leak is possible (adversarially proven: `150_scope_label_resolution_rpc.sql` cases 7–14 cover forged claims, multi-family unions, orphaned rows, and injection-shaped data, all correctly isolated to the caller's own children), but the mechanism is a genuine third shape ADR-0019's text doesn't name.

### Options Considered
- **Extend the exemption to cover it (chosen)** — Pros: matches ADR-0019's own stated rationale — the audit trail exists for "the oversight case" (staff viewing a child that isn't self/parent-scoped), not routine identity-scoped reads of one's own children regardless of which role happens to be active in the session; a parent opening the role switcher is not the scenario non-negotiable #6 is guarding against. Keeps the working, tested product requirement (switcher shows every held role's label at once) intact with no code change. Cons: the unaudited exemption is no longer defined purely by mechanism ("plain RLS-select") — it now also covers a `SECURITY DEFINER` shape, so future reviewers/auditors need this ADR, not just ADR-0019, to see the full boundary.
- **Audit every parent-branch read** — Pros: strictly conservative reading of non-negotiable #6 ("audit_log on access" to any minor's record via any mechanism). Cons: would write an `audit_log` row every time any user with a parent role opens the role switcher, cluttering the audit trail with routine UI reads and diluting its signal for the actual oversight case; also inconsistent with ADR-0019's own rejected option ("full RPC/view wrapper for all minors'-record reads... avoidable overhead for a case that isn't the compliance concern in practice").
- **Gate the parent branch on `active_role = 'parent'`** — Pros: mechanism would then match `students_parent_select` exactly, no new decision needed. Cons: breaks the actual, already-tested product requirement — the switcher must show labels for every held role simultaneously, confirmed by `150_scope_label_resolution_rpc.sql` case 2; would mean regressing shipped functionality solely to avoid writing this ADR, the wrong trade.

### Decision
The unaudited self/parent-scope exemption in ADR-0019 extends to cover `SECURITY DEFINER` reads of a minor's record, **provided** the read is provably restricted to rows the caller owns by identity (`auth.uid()`), independent of which `active_role`/scope claim is present in the session — not just plain RLS-scoped `select`. `resolve_my_scope_labels()`'s parent branch qualifies under this test today, proven by the adversarial suite in `supabase/tests/150_scope_label_resolution_rpc.sql` (cases 7–14: no cross-family leakage, forged claims have zero effect, orphaned rows never leak, isolation holds under real distinct users).

Any future function of this shape (a `SECURITY DEFINER` RPC surfacing self/parent-scoped minors' data, active-role-agnostic) inherits this exemption **only if** it carries an equivalent adversarial proof — cross-identity isolation under forged claims, at minimum. It does not extend to any read that can return another family's data under any claim combination; that remains squarely pathway (b) (audited, scope-checked).

### Consequences
- `20260714224917_resolve_my_scope_labels_rpc.sql` / `20260715030000_resolve_parent_scope_label.sql` should get a short comment citing this ADR, so a future reader doesn't have to rediscover the reasoning from test behavior alone.
- No `audit_log` write is added to `resolve_my_scope_labels()`; its existing adversarial coverage (cases 7–14) is the standing proof obligation for staying inside this exemption, and any change that weakens that isolation invalidates the carve-out.
- Owner: **System**, folded into `core-schema-and-rls` as a documentation follow-up (code comment only, no schema/RLS change) — no new migration required.
- **Residual risk:** if a future function of this shape can't produce equivalent adversarial proof of identity-only scoping, it does not get this exemption by default — treat it as pathway (b) (audited) until proven otherwise.
