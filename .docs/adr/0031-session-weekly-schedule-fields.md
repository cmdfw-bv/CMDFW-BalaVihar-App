# ADR-0031: Sessions carry a fixed weekly schedule (`day_of_week`, `start_time`, `end_time`) — core-schema-and-rls amendment; supersedes attendance-ui's raw-`today` date default

**Status:** Closed · **Date:** 2026-07-24 · **Deciders:** Project owner + architect
**Governs:** System → `core-schema-and-rls` (`.docs/specs/System/core-schema-and-rls.md`, Built) — amends its canonical schema (acceptance criterion #1). Also amends Teacher → `attendance-ui` (`.docs/specs/teacher/attendance-ui.md`, Design ✓/signed-off/`/plan` ✓) — its date-default decision assumed a fact that turns out to be false for real Bala Vihar sessions.

### Context
Real center/session data surfaced for the first time (project owner, 2026-07-24): three centers (Saaket, Frisco, Chitrakoot) run eight named sessions, each on **one fixed weekday at one fixed time** — e.g. Saaket S4 meets Fridays 6:45–8:15PM; all others meet Sundays across three time bands (9:00–10:30AM, 12:00–1:30PM, 2:00–3:30PM). The pilot POC targets **Frisco F3 (Sunday 2:00–3:30PM)**.

The current schema (`sessions`: `id, center_id, name, start_date, end_date`) has no column for weekday or time-of-day — `start_date`/`end_date` model the enrollment-period range (e.g. a term), not which day of the week the session's classes actually meet. Nothing upstream of this ADR (doc 1, doc 2, doc 3, core-schema-and-rls) ever specified a weekly recurrence, so this was a true gap, not a design oversight within any one item.

This gap is not cosmetic: `attendance-ui`'s already-signed-off design defaults its date selector to `todayIso()` — raw current date, unconditioned on whether today is a day the session meets at all. For Frisco F3, opening the screen on any day but Sunday defaults to a date with no possible class meeting.

### Options Considered
- **Add `day_of_week` + `start_time` + `end_time` to `sessions`** (chosen) — Pros: matches the real 1:1 mapping between a named session ("Frisco F3") and one fixed weekly slot; every class under a session inherits the same schedule, so the field belongs at the session level, not duplicated per class; small additive migration (three nullable-then-backfilled-then-not-null columns), doesn't touch any existing FK/RLS shape. Cons: amends a **Built**, tested (73/73), live-verified item — requires a new migration + pgTAP coverage, not a free change.
- **Add the fields to `classes` instead** — Pros: none identified beyond superficial flexibility. Cons: every class in a session already shares one schedule in the real data (grade-band classes under the same session meet at the same time); pushing the field to `classes` would just duplicate the same three values across every class row in a session and invite drift (two classes in one session disagreeing on their meeting time, which cannot happen in reality). Rejected.
- **Model a separate `session_schedule`/recurrence table** (for future multi-slot-per-session cases) — Pros: would generalize if a session ever needs more than one weekly slot. Cons: no such case exists in the confirmed real data (every session is exactly one weekday/time); building for a hypothetical not requested by any doc is exactly the premature abstraction the constitution's engineering guidance rules out. Rejected — revisit only if a real session with >1 weekly slot surfaces.
- **Leave schema alone; compute "today" client-side against a hardcoded weekday per session name** — Pros: zero schema change. Cons: encodes business data (which day each session meets) as a string-matched constant in client code instead of a queryable column — directly contradicts "schema is code" (constitution non-negotiable #3) and breaks the moment a session's schedule changes or a new session is added; rejected outright.

### Decision
1. **`sessions` gains three columns:** `day_of_week smallint not null check (day_of_week between 0 and 6)` (0=Sunday..6=Saturday, matching Postgres `extract(dow from ...)` convention so date-arithmetic doesn't need a translation table), `start_time time not null`, `end_time time not null`. Migration ships as an amendment to `core-schema-and-rls` (new timestamped migration file, not an edit to the existing one), with a matching pgTAP addition proving the check constraint and that existing RLS/grants on `sessions` are unaffected by the new columns.
2. **`attendance-ui`'s date-default decision is revised:** the screen's default `selectedDate` is no longer raw `todayIso()`. It becomes "the most recent scheduled meeting date for this session's `day_of_week` that is on or before today" (i.e. walk back ≤6 days from today to the last matching weekday; if today itself matches, use today). This replaces the relevant decision/pseudocode in `attendance-ui.md`/`attendance-ui.plan.md` — flagged there, not rewritten in full here, since that revision is `/design`'s job, not `/architect`'s.
3. **Date-nav bounds are unaffected in shape** (still clamps to `[session.start_date, min(today, session.end_date)]` per the existing decision) but prev/next should step by the session's weekday cadence (±7 days) rather than ±1 day, since intermediate days have nothing to mark — also a `/design` revision, flagged not solved here.
4. **Seed data** (core-schema-and-rls acceptance criterion #10, synthetic-only) is updated to include the real center/session catalog's *shape* (3 centers, 8 sessions with correct weekday/time) as synthetic rows — no real student/family PII, matching the existing synthetic-seed constraint.
5. **Pilot scope confirmed:** Frisco F3 (Sunday, 2:00–3:30PM) is the single session the POC pilot targets, per doc 1 §2/§9 and doc 2 §5 ("one center, one session") — those sections are updated to name the concrete session rather than stay generic.

### Consequences
- `core-schema-and-rls.md` gets a new decision + acceptance-criterion addendum (its canonical schema table for `sessions` gains the three columns); its Stage line notes this amendment landed after the original `/build`/`/test` pass, before `/deploy-staging` — so it can be folded into the same not-yet-staged deploy rather than a hotfix after promotion.
- `attendance-ui.md`/`attendance-ui.plan.md` are flagged (not silently overwritten) as needing a `/design` revision pass before `/migration` proceeds: the date-default and prev/next-step logic both depend on the new `sessions` columns, which don't exist yet.
- Doc 1 (§2 row, §9 title) and doc 2 (§5 title, §6 open items) are updated with the confirmed real center/session catalog and the Frisco F3 pilot target, replacing generic "one center, one session" phrasing.
- **Residual scope:** this ADR does not model holiday/skip-week exceptions to the weekly cadence (e.g. a Sunday with no class due to a holiday) — if that surfaces as a real pilot need, it's a follow-up ADR (likely an exceptions/blackout-dates table), not assumed here.
