# ADR-0029: Sankalp component kit ships as one System-owned unit (full-library exception to §12.12 per-capability ownership)

**Status:** Closed · **Date:** 2026-07-18 · **Deciders:** Project owner + architect

### Context
`.docs/3_ARCHITECTURE.md` §12.12 assigns each capability to its **owning persona's** spec — e.g. `FeedCard` would normally belong to Student/Parent feed, `ChatBubble` to chat, `ComplianceBar` to the Coordinator dashboard, `CsvImport`/`UserRoleRow` to Admin. Issue #18 ("Build the reusable Sankalp component kit") asks for the entire `design/sankalp/` component surface — `core/*` (8), `brand/*` (1 remaining: `EventDateBlock`), and all of `bv-connect/components/**` (16, across `comments/privacy/chat/admin/navigation/dashboard/feed/notifications/auth`) — ported as one deliverable, ahead of any of those owning features being built. Left under the default rule, each persona feature would independently re-port its own slice of the same reference components before its own feature work could start, duplicating effort and staggering the parallelism §12.6 is designed around.

### Options Considered
- **One System-owned kit, full library, presentational-only** (chosen) — Pros: every persona feature spec can build immediately against a common, tested, on-brand primitive set without first re-deriving its own component port; matches the explicit owner instruction; keeps data-wiring ownership with each feature (kit ships props-only, no Supabase/RLS access) so §12.12's ownership rule still governs *behavior*, just not *presentational porting*. Cons: one large item instead of several small ones; a component's presentational shape and its data-wiring land in different specs/PRs, so a future contributor must know both files.
- **Split per owning persona, feature-by-feature** (the §12.12 default) — Pros: matches the documented ownership model exactly; component + its data wiring stay in one spec. Cons: `ChatBubble`, `FeedCard`, `ComplianceBar`, etc. would each block their owning feature's start on a fresh design-kit port, re-deriving the same token/testing/gallery-harness scaffolding 6+ times; directly reintroduces the blocking problem #18 was filed to remove.
- **Partial kit now (core/* + brand/* only), defer domain components to each owning feature** — Pros: smaller single item, stays closer to §12.12. Cons: the domain components (`ChatBubble`, `FeedCard`, `ComplianceBar`, `CsvImport`, etc.) are exactly the pieces most likely to be re-derived inconsistently across parallel features — the partial version keeps the duplication risk the full-library version was meant to close. Rejected — doesn't solve the stated problem.

### Decision
The Sankalp component kit (issue #18) ships as **one System-owned item**, covering the **full component inventory** — `core/*`, `brand/EventDateBlock`, and all 16 `bv-connect/components/**` domain components — as an explicit, scoped exception to §12.12's per-capability ownership default. The exception is narrow: **presentational porting only**. Each component's **data wiring** (Supabase queries, RLS-scoped fetches, business logic that consumes the ported component) remains owned by that component's natural persona feature spec when that feature is later built — this item never touches Supabase, RLS, or privileged operations (kit components are prop-driven only, per `client-privacy.md`). Already-shipped, already-tested nav-shell surface (`components/AppHeader.tsx`, `components/RoleSwitcher.tsx`, `app/(auth)/sign-in.tsx` from #17) is left untouched; `RoleBadge`, `PersonaSwitcher`, and `MagicLinkLogin` ship as independent kit primitives without retrofitting or merging into that shipped surface.

### Consequences
- `.docs/specs/system/sankalp-component-kit.md` is the spec of record for every ported component's **presentational** contract; each owning persona's later feature spec cross-references it for data-wiring, per §12.12's "consumers cross-reference, never copy" rule.
- A future architect reviewing a persona feature spec (feed, chat, dashboard, admin, notifications) that consumes `FeedCard`/`ChatBubble`/`ComplianceBar`/etc. should expect the component's presentational half to already exist here — the feature spec only need scope the data-wiring half. This ADR is the record that the discrepancy from §12.12 is intentional, not an oversight.
- `RoleSwitcher.tsx`/`sign-in.tsx` vs. the kit's `PersonaSwitcher`/`MagicLinkLogin` staying unreconciled is a deliberate, disclosed gap (not a bug) until/unless a future item scopes reconciling them.
- `EventDateBlock` ships with no consumer screen — flagged dead-code risk until an events feature exists; do not invent a consumer to exercise it.
