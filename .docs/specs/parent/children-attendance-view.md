## Requirements (refined)

### User story
As a Parent, I want to see a list of my children and each child's attendance stats (present / absent / %) so that I can stay informed about their participation without having to ask the teacher or coordinator.

### Decisions captured during refine
- **No new schema or RLS.** `core-schema-and-rls` already ships a plain `SELECT` RLS policy on `students`/`attendance` scoped to "own children" (`family_id` in the caller's linked families via `family_members`) — direct and **unaudited by design** (ADR-0019: Parent viewing their own child is the subject's-own-parent case, not the oversight case `audit_log` exists for). This item is a pure client build against existing tables; it must use the plain RLS-scoped `select`, never a staff RPC.
- **Attendance % denominator = marked rows only.** There is no class-meeting-schedule table — an `attendance` row exists only once a Teacher marks a date present/absent (`core-schema-and-rls` design). So `% = present / (present + absent)` over whatever has been marked so far; there is no "expected total classes" concept to compute against.
- **Scope = current active enrollment only** (confirmed with human, 2026-07-24). A child's attendance % reflects only their current session's active enrollment (`enrollments.status = 'active'`), not an all-time aggregate across past/withdrawn enrollments. If a family need for historical/cross-session stats surfaces later, that's a follow-up item, not solved speculatively here.
- **List membership = actively-enrolled children only** (confirmed with human, 2026-07-24). The children list shows children with an active enrollment this session. A child with no active enrollment (e.g. withdrawn, or not yet enrolled) does not appear as a row with a broken/zero stat — they're simply not part of this list. (Whether a family ever needs to see a withdrawn child here is out of scope until a real need surfaces.)
- **Screen fills an existing nav slot.** `client-auth-session-and-nav` already registers the `attendance` tab and maps it to Parent ("view children's") with placeholder content. This item replaces that placeholder — it does not add a new route.

### Acceptance criteria
1. **Children list.** For the signed-in Parent's `active_role = 'parent'`, the screen lists every `students` row where `family_id` is in the caller's linked families (via `family_members`) **and** has an active enrollment (`enrollments.status = 'active'`) in the current session. One row per child: name, class/grade, and the child's attendance %.
2. **Per-child attendance stats.** For each listed child, compute present count, absent count, and `% = present / (present + absent)` (rounded) over `attendance` rows joined through that child's current active enrollment. A child with zero marked attendance rows shows an honest "no attendance recorded yet" state, not `0%` or `NaN`.
3. **Read path.** Data access uses the plain RLS-scoped `select` against `students`/`enrollments`/`attendance` (own-children scope) — no staff RPC, no new `audit_log` entries generated by this screen (per ADR-0019).
4. **Four-state UI** (`StateView`, per `client-auth-session-and-nav`'s ADR-0014 DoD): loading · empty (family has zero actively-enrolled children) · error (with retry) · content.
5. **Component reuse.** Built from the Sankalp kit: `ListRow` for each child row, `StatTile` (tabular-nums) for the present/absent/% figures, `StatusChip` if a compact per-child status indicator is useful, `StateView` as the four-state wrapper. No new kit primitives required by this scope.
6. **Multi-child households.** A family with more than one actively-enrolled child sees every one of them as its own row with its own independently-computed stats — no cross-child or cross-family bleed (relies on `core-schema-and-rls`'s existing adversarial-tested own-children scope; this item does not re-prove RLS, only consumes it correctly).
7. **No cross-scope reach.** The screen must not be able to see another family's children under any input — this is an RLS guarantee already proven by `core-schema-and-rls`; this item's own test coverage confirms the *client query* only ever requests the caller's own scope (defense against a client-side bug that would otherwise rely solely on RLS to save it).
8. **Responsive + design DoD.** Renders correctly at the four breakpoints (360/768/1024/1440); tokens (no hex); tabular-nums on all attendance figures; ≥44px touch targets — per `design-system` skill / Sankalp `USAGE.md`.

### Edge cases
- **Zero actively-enrolled children.** A Parent account linked to a family with no currently-active enrollments (e.g. between sessions) sees the empty state, not an error.
- **Zero marked attendance for an otherwise-active child.** New enrollment, first week of the session, no class meetings marked yet — show "no attendance recorded yet," not a misleading `0%`.
- **Multiple guardians, same family.** Two parent accounts linked to the same `family_id` (ADR-0018) both see the identical children list/stats — no per-guardian filtering beyond family membership.
- **Long child/class names** at the 360px breakpoint must truncate in `ListRow`, not wrap/overflow (existing kit contract).

**POC-core** (doc 2 §2, Parent). Was blocked by `client-auth-session-and-nav` (#17, merged) and `sankalp-component-kit` (#18, merged 2026-07-24) — both blockers now lifted; this item is unblocked.

### Consumers (cross-persona)

### Access scope (§5.4)

### Explicitly out of scope (so a later item picks it up)

- Teacher's "mark & submit attendance" and "report absence" (separate Teacher-owned item, doc 2 §2).
- Coordinator's compliance dashboard / cross-child rollups (separate Coordinator-owned item).

- Showing withdrawn/not-yet-enrolled children in the list (confirmed out of scope above).
- Push/email notifications about attendance changes (separate `notifications-infra` System item; this screen is pull, not push).

## Design (detailed spec)

> **Design decisions captured this pass:**
> 1. **Single query, existing RLS only.** One `enrollments` read with nested embeds (`student:students(...)`, `class:classes(...)`, `attendance(status)`) filtered to `status = 'active'` — PostgREST applies each table's own RLS policy independently to every embedded relation, so the nested `students`/`classes`/`attendance` rows are scoped by `students_parent_select`/`classes_parent_select`/`attendance_parent_select` regardless of the join shape. This satisfies AC#7 (client query itself only ever *requests* the caller's own scope — `.eq('status', 'active')` plus the caller's own JWT, no cross-family parameter possible) without adding a second round trip.
> 2. **"Current session" stays implicit.** Per the architect's note (`sessions` has no `is_current` flag — one-live-session-at-a-time is a business assumption, not schema-enforced), the query does **not** filter by `session_id`. `enrollments.status = 'active'` combined with the existing `enrollments_one_active_per_session` partial unique index already yields at most one row per child under that assumption — adding a client-side "current session" resolution would be solving a problem `core-schema-and-rls` explicitly deferred, not this item's to pick up.
> 3. **Percent/mapping logic lives in a pure module**, not inline in the fetch hook — `lib/attendance/parent/childAttendanceStats.ts` (`computeAttendanceStats`, `mapEnrollmentRow`), unit-testable without a live Supabase call. Matches the kit's own `*.logic.ts` convention (`StatTile.logic.ts`, `StateView.logic.ts`) and the constitution's TDD rule (test the rounding/null-percent behavior directly, not through a mocked network call).
> 4. **No bv-connect screen-composition reference exists for this layout** — confirmed via `DesignSync.list_files` against the live Chinmaya Mission Design System project: no `parent`/`children`/`attendance`-domain entry under `bv-connect/components/**`, and `bv-connect/screens/**` isn't domain-specific. Same gap `teacher/attendance-ui` (issue #20) hit and resolved the same way: compose from existing core primitives rather than block on a screen that was never authored upstream. `ListRow` and `StateView` themselves have **no bv-connect source at all** — `sankalp-component-kit`'s own spec already recorded "no existing reference" for both and authored them fresh in `components/core/`; only `StatTile`/`StatusChip` carry a live `bv-connect/components/core/*.jsx` reference. Nothing to sync back to the mirror — this is a genuine upstream gap, not a stale local copy.
> 5. **`app/(tabs)/attendance.tsx` becomes a thin role dispatcher, not a Parent-only rewrite.** The tab is shared across Student ("view own"), Parent ("view children's"), and Teacher ("mark/submit") per `client-auth-session-and-nav`'s nav map — today's stub renders the same placeholder for every role. This item adds an `activeRole === 'parent'` branch to render the new screen and leaves every other role on the existing placeholder text, so it doesn't foreclose Student's or Teacher's still-separate attendance items.
> 6. **Parent's files are namespaced under `lib/attendance/parent/`**, not flat in `lib/attendance/`. Teacher's attendance-ui (issue #20, separate unmerged branch) already claims flat names in that directory (`useAttendanceRoster.ts`, `AttendanceRosterRow.tsx`, `rosterMap.ts`, …) for a different read/write concern; a `parent/` subfolder avoids a same-directory naming collision at merge time without needing to coordinate branches now.

### Behavior
- **`useChildrenAttendance()`** (`lib/attendance/parent/useChildrenAttendance.ts`) runs the query on mount: `supabase.from('enrollments').select('id, student:students(id, first_name, last_name), class:classes(name, grade_band), attendance(status)').eq('status', 'active')`. Returns `{ state: ViewState, children: ChildAttendance[], errorText?: string, refetch: () => void }`.
- **State derivation** (matches `StateView`'s `ViewState = "loading" | "empty" | "error" | "content"`, `components/core/StateView.logic.ts`): `loading` while the request is in flight; `error` if the request rejects (`refetch` re-runs the same query, no cached partial data shown); `empty` if it resolves with zero rows (AC edge case: no actively-enrolled children); `content` once one or more rows resolve.
- **Row mapping** (`childAttendanceStats.ts`): each `enrollments` row → `mapEnrollmentRow(row)` → `{ enrollmentId, studentId, name: "${first_name} ${last_name}", className: class.name, gradeBand: class.grade_band, ...computeAttendanceStats(row.attendance) }`. `computeAttendanceStats(records)` counts `present`/`absent` from the embedded `attendance` array and returns `percent: total === 0 ? null : Math.round((present / total) * 100)` — `null` is the explicit "no attendance recorded yet" signal (AC#2), never coerced to `0`.
- **Sort:** children rendered in `first_name` order — stable, predictable; not an acceptance criterion, just a default (no requirement to reorder by class/percent).
- **Screen** (`app/(tabs)/attendance.tsx`, Parent branch): `useRoleGuard("attendance")` (unchanged — tab-membership guard already exists) → if `activeRole === 'parent'`, mount `ParentAttendanceScreen` (`lib/attendance/parent/ParentAttendanceScreen.tsx`), which calls the hook and renders `<StateView state={state} emptyText="…" errorText="…" onRetry={refetch}>` wrapping a scrollable list of `ChildAttendanceRow`s.

### Data & RLS impact
**No new schema, migration, or RLS policy** (per Requirements) — this item consumes four already-shipped policies unchanged, all from `supabase/migrations/20260709032818_core_operational_rls_policies.sql`:

| Policy | Table | Scope |
|---|---|---|
| `students_parent_select` | `students` | `exists (family_members fm where fm.family_id = students.family_id and fm.user_id = auth.uid())`, gated on `active_role = 'parent'` |
| `enrollments_parent_select` | `enrollments` | same family-membership chain via `students` |
| `attendance_parent_select` | `attendance` | same chain via `enrollments → students` |
| `classes_parent_select` | `classes` | same chain via `enrollments → students` |

- **No `audit_log` writes** — ADR-0019's exemption (Parent viewing their own child is the subject's-own-parent case, not the oversight case audit exists for) applies directly; this read path was already confirmed unaudited-by-design at `/architect`.
- **Defense-in-depth, not reliance:** the `.eq('status', 'active')` filter is a client-side narrowing for correctness (AC#22/scope = current active enrollment), not a security boundary — a Parent client that omitted it would still only ever see their own family's rows, per RLS. AC#7's own test coverage (below) proves the query itself stays narrow regardless.
- **Adversarial RLS test additions:** none required — `core-schema-and-rls` already carries adversarial role × scope coverage for these four policies (per architect review). This item's own test coverage is client-side only: confirm the built query requests `status = 'active'` and no other family's id, per AC#7.

### API / module surface (`lib/attendance/parent/`)
- `useChildrenAttendance.ts` — fetch hook: issues the query, derives `ViewState`, exposes `refetch`.
- `childAttendanceStats.ts` — pure: `computeAttendanceStats(records)`, `mapEnrollmentRow(row)`, exported `ChildAttendance` type.
- `ChildAttendanceRow.tsx` — presentational: one child's `Card` + `ListRow` + stats (see UI below).
- `ParentAttendanceScreen.tsx` — composes the hook + `StateView` + a list of `ChildAttendanceRow`.

### File / route changes
- **New:** `lib/attendance/parent/{useChildrenAttendance,childAttendanceStats,ChildAttendanceRow,ParentAttendanceScreen}.ts(x)` + matching `__tests__/childAttendanceStats.test.ts`.
- **Modified:** `app/(tabs)/attendance.tsx` — route on `activeRole` (decision #5).

  **Corrected 2026-07-30 (PR #51 review):** the original wording — *"every other role keeps today's placeholder unchanged"* — stopped being true once #49 landed the Teacher roster on this same route. `ROLE_TABS` (`navMap.ts`) grants `attendance` to **student, parent and teacher**, and `useRoleGuard` only redirects roles that are *out* of scope, so all three mount this screen. The shipped shape is now an exhaustive `switch`:

  | Role | Screen |
  |---|---|
  | Parent | `ParentAttendanceScreen` (this item) |
  | Teacher | `TeacherAttendanceScreen` (issue #20) |
  | Student | placeholder — **own attendance view not built yet** (doc 2 Student backlog) |

  Student is handled explicitly rather than falling into an `else`: `useAttendanceRoster` calls `get_class_roster_for_staff`, which authorizes only teacher/coordinator/bv_coordinator/admin and writes an `action='denied'` audit_log row for anyone else — so an unhandled Student would emit a denied audit row on every visit to the tab, on a minors'-data governance surface. Verified live 2026-07-30: Student sees the placeholder, denied audit rows 0 before → 0 after.

### UI
**No bv-connect screen reference** (decision #4) — composed from four already-referenced core primitives, each individually matched to its own source:
- `ListRow` — `components/core/ListRow.tsx` (kit-authored; no bv-connect source, per `sankalp-component-kit`).
- `StatTile` — `bv-connect/components/core/StatTile.jsx` (+ local mirror `design/sankalp/components/core/StatTile.jsx`), unchanged — mono/tabular-nums variant for Present/Absent/%.
- `StatusChip` — `bv-connect/components/core/StatusChip.jsx` (+ local mirror), `status="neutral"`, used for the per-child "no attendance recorded yet" indicator (AC#5's "if a compact per-child status indicator is useful" — this is that case).
- `StateView` — `components/core/StateView.tsx` (kit-authored; no bv-connect source), the four-state wrapper for the whole screen.

**Per-child composition** (`ChildAttendanceRow`): a `Card` (`tone="surface"`, default padding) containing a `ListRow` (`title`: child's full name, `subtitle`: `"{className} · {gradeBand}"`, no `leading`/`trailing` — nothing in the requirements calls for an avatar) followed by either:
- three `StatTile`s in a row (`Present`, `Absent`, `Attendance %`) when `percent !== null`, or
- a single `StatusChip status="neutral"` reading "No attendance recorded yet" when `percent === null` — replacing the stat row for *that child only*, distinct from the screen-level `empty` state (AC edge case: this is a partial/per-row honest-empty, not a whole-screen one).

**Design DoD:** `ListRow`'s existing `numberOfLines={1}` on title/subtitle covers the 360px truncation edge case (no new work — existing kit contract). `StatTile`'s mono/tabular-nums variant covers "tabular numerics for compared numbers." `theme.chrome.hitMin` on `ListRow` covers ≥44px touch targets. No hex literals — all new styling composes `theme` tokens same as every other kit consumer. No permission-denied state — out-of-scope roles never reach this branch (`useRoleGuard` + the `activeRole` check in decision #5).

### Edge cases (design detail)
- **Zero actively-enrolled children** — `StateView` `empty` state, screen-level (Behavior above); distinct from the per-child no-data case below.
- **Zero marked attendance for an otherwise-active child** — per-child `StatusChip` "No attendance recorded yet" (UI above), never `0%`/`NaN` — `computeAttendanceStats` returns `percent: null` explicitly, not a coerced zero.
- **Multiple guardians, same family** — no per-guardian filtering added; both accounts hit the identical RLS-scoped query and see the identical result set, by construction (no special-case code needed).
- **Long child/class names at 360px** — `ListRow`'s existing single-line truncation (`components/core/ListRow.tsx:20-21`), not new work.
- **Query failure** — `StateView` `error` state, `onRetry` wired to the hook's `refetch`, per the kit's existing retry contract (`StateView.logic.ts`'s `shouldShowRetry`).

- Teacher's "mark & submit attendance" / "report absence" and Student's "view own attendance" — separate, differently-scoped items sharing the same tab slot (decision #5 only adds Parent's branch).
- Coordinator's compliance dashboard / cross-child rollups.
- Historical/all-time attendance across past sessions or withdrawn enrollments.
- Showing withdrawn/not-yet-enrolled children in the list.
- Push/email notifications about attendance changes.
